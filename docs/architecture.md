# 多用户服务化架构设计

目标：把 getjobs-agent 从本地单用户工具演进成支持多人并发使用的对外服务。

## 现状约束

当前 get_jobs 是单用户单例架构，直接并发会导致用户间状态污染：

- `PlaywrightManager` 是 Spring 单例，一个 Chromium 实例、每个平台一个 Page
- 登录态（Cookie）存在单份 SQLite，无 user_id 维度
- 浏览器 profile 固定为 `browser-data/`，CDP 端口固定 7866
- 配置表（`boss_config`、`cookie`、`ai` 等）均为单行全局配置
- 后台任务无队列，`isRunning` 是全局布尔值

结论：**不能靠改表结构实现多租户，必须做进程/容器级隔离。**

## 目标架构

```
用户 A/B/C ──聊天──> 控制面（鉴权、配额、计费、任务队列、会话路由）
                        │  按 user_id 路由
                        ▼
        runner-A 容器            runner-B 容器
        ┌────────────────┐      ┌────────────────┐
        │ get_jobs :9527 │      │ get_jobs :9527 │
        │ getjobs-mcp    │      │ getjobs-mcp    │
        │ Chrome+profile │      │ Chrome+profile │
        │ 卷: db+登录态   │      │ 卷: db+登录态   │
        └────────────────┘      └────────────────┘
```

### 控制面（新写）

- 账号体系、JWT 鉴权、套餐与配额
- `user_id → runner endpoint` 路由表
- 每用户任务队列（同一账号投递任务串行）
- 会话记录、审计日志、用量统计
- 唯一公网入口；runner 只在内部网络暴露

### Runner（get_jobs 容器化）

- 每用户一个容器实例，包含 get_jobs 后端、getjobs-mcp、Chrome（Patchright）
- 两个持久卷：
  - `db`：`getjobs.db`（配置、Cookie、投递记录）
  - `browser-data`：Chrome 用户目录（登录态）
- 端口动态分配，内部注册到控制面
- 空闲回收：N 分钟无操作后挂起或停止容器，卷保留；下次使用再拉起

### 登录流程

1. 用户在聊天里点"登录 Boss"
2. 控制面调用目标 runner 打开登录页，截取二维码/登录页截图
3. 图片经聊天通道推给该用户
4. 用户手机扫码，runner 轮询登录状态并回调控制面
5. 登录态只写入该用户自己的卷

### 数据隔离

- 最省改动：保留每用户独立 SQLite 卷，控制面数据库单独存账号/会话/用量
- 若需要跨用户统计：控制面上报脱敏后的投递事件到 Postgres（带 user_id）
- 任何跨用户查询都必须显式带 tenant 维度

### 并发与容量

| 项目 | 估算 |
|---|---|
| 单 runner 内存（Boss 单平台） | 0.5–1 GB |
| 4C8G 机器活跃 runner | 4–6 个 |
| 超出容量 | 排队，按套餐优先级调度 |
| 单账号投递上限 | Boss 约 150 次打招呼/天，按账号限流 |

### 安全

- runner 不对公网暴露；控制面到 runner 使用内网 token
- MCP 工具层保持无全局状态，`GETJOBS_BASE_URL` 由控制面注入
- agent 不直接访问数据库和浏览器，只走白名单工具
- 日志与截图中不得出现 Cookie、API Key、简历内容

## 实施阶段

1. **容器化**：Dockerfile（JDK 21 + Chrome + Patchright）、卷挂载、健康检查、动态端口
2. **控制面 MVP**：用户/鉴权、runner 注册与路由、任务队列
3. **登录中转**：二维码截图推送到聊天
4. **计量与限额**：每日投递次数、并发数、用量统计
5. **弹性**：空闲回收、按需拉起、多机调度

## 风险

- **许可**：上游 get_jobs 为 PolyForm Noncommercial 1.0.0，对外商业运营需先获得作者授权
- **平台风控**：多租户代投属于平台协议明确禁止的规模化行为，封号与法律风险随用户数放大
- **出口 IP**：同机房 IP 集群投递易被整段风控，需要按用户/批次隔离出口
- **建议**：优先考虑"服务只做编排与建议，投递在用户本机执行"的轻量模式，降低集中风险
